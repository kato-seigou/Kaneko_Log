# やりたいこと
カネコアヤノの聞いた記録を保存するWEBアプリの作成

# 機能
- ユーザー登録
- ユーザーが効いた曲がタイムラインに流れてくる
    - いいねやコメント、フォロー機能はない
- ユーザーのみが自分自身の統計を見ることができる
- カネコアヤノのディスコグラフィのみしか反映できない

# モチベーション
- カネコアヤノの曲をいつどんな時に効いているかを知りたい
- プレイリストで聞くのが主流の中でどれだけフルアルバムで聞いているか

# 1) 目的
- 聞いたカネコアヤノの曲を記録するアプリ
- ユーザーはカネコアヤノファンを対象
- 作るもの
    - 必要最低限の機能
        - 記録に特化
        - 若干、共有が可能
- 作らない物
    - 大規模な機能
        - like Twitter, Instagram

# 2) 画面とユーザー体験
## 画面
- ユーザー登録画面
    - 最初のユーザー登録
    - パスワードとIDを登録する
- ログイン画面
    - ログイン画面
    - IDとパスワードを入力する
- タイムライン画面
    - ただひたすら登録された曲記録が流れてくる
- 記録画面
    - 聞いた曲と時間を登録する
        - 聞いた曲はカネコアヤノのディスコグラフィから開発者の方でリストとして登録済み
        - 時間は現在時刻をデフォルトにして、自分でも設定できるようにする
- 統計可視化画面
    - 何とかする
    - とりあえず、自分のログだけを見れるようにする
## 画面遷移
- ユーザー登録からはタイムラインへ
- ログイン画面からはタイムラインへ
- タイムラインからは記録画面と、統計画面へ
- つまりタイムラインをホーム画面とする
- Twitterの様なUIを目指す

# 3) 機能要件
### ユーザーが体験できること
- いつカネコアヤノの曲を聴いたかを登録できる
- ほかのユーザーがどんな曲を今聞いているのかがわかる
### 登録できないこと
- 本アプリはセキュリティを最低限にしたい
- つまり、個人情報に直結する要素は登録できないようにする
    - 位置情報
    - 本名
    - 写真
    - 生年月日
-

# 4) データ設計
## データ設計
### 曲リスト（これはdbじゃなくてもいいかも）
- ルール
    - 重複禁止
- カネコアヤノのディスコグラフィに関する情報
    - 作成年月
    - ディスコグラフィをフルで再生したときの時間
- discography_title: ディスコグラフィのタイトル
- discography_playtime: フル再生時間
- released_datetime: 作成年月日
- discography_id: ディスコグラフィの通しID
### ユーザー情報
- ルール
    - user_idで管理されるのでuser_nameは重複可能
- user_id: 自動的に付与される番号
- user_name: ユーザーが自分で登録できる
    - アルファベットと記号のみで10文字以内
    - 変更可能
- password: ログイン用のパスワード
    - TODO これってセキュリティ案件だけど、どうするのかな？
    - password_hashを保存
        - passlib[bcrypt]
### 聞いた曲のログ
- ルール
    - listened_idで管理されるので重複可能
    - 情報の削除可能
- listened_id:  一応、聞いた曲のID
- user_idごとに作成するつもり
- listened_datetime: datetime型で視聴時間を記録
- discography_title: ディスコグラフィのタイトル
    - ここは曲リストのdiscograpy_idと紐づけるのが良いかな

# 5) API設計
## リソース設計
- users 
- discographies
- listen_logs
> この3つに対して、「作る、読む、更新、削除」をどう提供するかがAPI設計の骨格

## 認証・認可（誰が何をできるか）
ログインしている人=本人を確実に判定できる仕組みが必要
- ログイン手段: セッションCookie方式/ JWT方式
    - 個人開発ではJWTがAPI単体で完結しやすくていい
- アクセス制御（認可）:
    - 自分のログ: 見れる・追加できる・編集できる・削除できる
    - 他人のログ: タイムラインで公開される範囲だけ見れる
    - 作品マスタ: 基本は読み取りのみ（管理者だけいじれる）
API設計としては最終的に
- どのエンドポイントがログイン必須か
- ユーザーIDをリクエストで受け取らない（受け取ると事故る） を決める

## エンドポイント設計（URL、HTTPメソッド）
- GET
- POST
- PATCH/PUT: 更新
- deleted_at
例
- 認証系
    - `POST /auth/register`
    - `POST /auth/login`
    - `POST /auth/logout` 
- 自分
    - `GET /me`　（自分のプロフィール）
    - `GET /me/listen-logs` 自分の記録用
    - `GET /me/status` 統計 
- 公開タイムライン
    - `GET /timeline` 全体の最新50件 + ページング
- 記録（作成、編集、削除）
    - `POST /listen-logs`
    - `PATCH /listen-logs/{id}`
    - `DELETE /listen-logs/{id}`
- 作品マスタ
    - `GET /discographies`
    - `GET /discographies/{id}`
